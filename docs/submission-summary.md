# PPT2 제출 요약 — REA 메모 앱

제출 기준: 2026-11-11 실제 앱 검증 완료 버전. 새 기능 추가 없이 소스·테스트·문서·정제 증거를 확정한다. 이 문서는 발표 자료 작성용이며 PPT 파일 자체는 아니다.

## 1. 과제와 결과

Google Keep의 제한된 UI 관찰을 출발점으로 로컬 메모 앱을 구현했다. 원본 서버를 복원한 것이 아니라, 관찰한 사실과 확인하지 못한 부분에 대한 자체 설계를 구분한 재현 과제다. Spring Boot·Thymeleaf·MySQL로 메모 작성부터 보관·검색·휴지통·체크리스트·라벨·고정·색상까지 구현하고 실제 앱 재시작 지속성을 검증했다.

## 4. REA 분석 과정과 증거

1. 사용자가 별도 분석 Chrome에서 로그인했다. `list_browser_targets`로 연결을 확인하고 `inspect_web_page`로 UI를 관찰했다.
2. 과제용 테스트 메모만 대상으로 `capture_browser_scenario`에서 입력·보관·보관 해제·같은 메모 재탐색을 수행했다. DOM·접근성·캡처를 교차 확인했다.
3. 원본의 전체 목록 이동과 검색·휴지통 후속 관찰에서는 연결 불가 안내가 확인됐다. 반복 변경을 시도하지 않고 해당 동작을 미확인으로 남겼다.
4. 앱 구현 후 CDP 9227에서 REA 시나리오로 실제 폼·버튼을 조작했다. 직접 만든 테스트 메모/라벨만 변경했다.
5. 서버를 두 번 재시작하고 페이지를 새로 요청해 저장·상태·삭제 결과를 비교했다. 개인정보가 없는 화면과 정제 기록만 저장했다.

## 5. 관찰 사실·자체 설계·미확인 구분

**원본 직접 관찰:** 지정 테스트 메모의 제목·본문, 보관 후 안내 문구와 버튼 변화, 보관 해제 후 버튼 복귀, 같은 세션의 동일 메모 재로드 후 내용·상태 유지. 고정/배경 옵션 버튼 존재도 기록돼 있다.

**우리 앱의 설계:** archived/trashed/pinned/color 필드와 체크항목·라벨 테이블, 명시적 저장 버튼, 보관 메모 검색 포함, 휴지통 일반 검색 제외, 삭제 전 보관 위치로 복원, 고정 우선 정렬, 5개 색상, 입력 길이 제한, UTC 시각, 별도 영구 삭제 확인 화면. Google의 실제 DB 구조를 알아냈다는 의미가 아니다.

**원본 미확인:** 전체 목록↔보관함 실제 이동, 제목·본문 검색 범위, 휴지통 이동·복원 위치·영구 삭제 확인창, 체크리스트·라벨·고정 정렬·색상 변경 결과, 원본 API·DB·동기화 내부 구조, 다른 기기 및 완전 종료 후 지속성, 픽셀 단위 UI 동일성. 우리 앱의 성공을 원본의 관찰 성공으로 바꾸지 않았다.

### 실제 앱 브라우저 확인 69개 — MySQL 앱

`observations.sanitized.json`의 시나리오 기록 59개 안에 명시적 DOM 확인 69개가 있고 모두 기대값과 일치했다. **69개 독립 테스트 케이스 또는 69개 기능이라는 뜻은 아니다.** 입력·클릭 단계 및 정제 설명을 포함하는 실제 브라우저 관찰 기록이다.

- 작성·수정 후 재조회, 제목·본문·체크항목 검색, 결과 없음 안내.
- 보관·해제와 전체/보관함 분리, 보관 메모 검색·라벨 조회 포함.
- 휴지통 검색·목록 제외, 일반/보관 메모 각각의 복원 위치와 내용 유지.
- 편집 URL 차단, 활성 메모 삭제 확인 거부, 영구 삭제 확인·취소·동의 후 삭제.
- 체크항목 추가·제거·체크/해제, 라벨 생성·이름 변경·지정·조회·삭제 후 메모 보존, 고정·색상.
- 공백 제목/본문과 내용 없는 `[x]` 저장 시 오류 안내.
- 서버 PID 39471→40114→40349로 두 차례 재시작. 첫 재시작은 일반·보관·휴지통 상태 유지, 두 번째는 최종 상태와 영구 삭제·라벨 삭제 유지. 테스트 라벨 페이지 HTML은 두 번 모두 전후 동일.

실행 Java의 MySQL 3306 연결을 확인했다. SQL 클라이언트로 행·버전을 별도 조회하거나 실제 DB 생성 시각 값을 비교하지 않았다. 잘못된 POST 상태 요청 전반, 강제 DB 실패 등은 H2/MockMvc 범위를 실제 브라우저 검증으로 확대하지 않는다. 이전 사용자의 작성·보관 수동 확인 보고도 Codex 직접 검증과 별도 기록이다.

## 8. 원본 대비 차이·제외 기능·남은 제한

- 카드 목록과 편집 구성을 참고했지만 별도 편집 페이지·명시적 저장·고정 색상 선택 UI를 사용한다. 원본과 화면/동작이 완전히 동일하다고 주장하지 않는다.
- 로컬 단일 사용자 과제 범위이며 로그인·권한·공유·다중 사용자·클라우드/기기 동기화·자동 저장·알림·첨부·그림·버전 기록은 구현하지 않았다.
- 휴지통의 기간 경과 자동 삭제는 제외했다.
- 자동화한 실제 브라우저 검증은 주요 흐름이며 모바일 전체·부하·동시 편집·강제 DB 장애·신규 환경 다운로드를 포괄하지 않는다.
- 실제 MySQL 스키마 validate 기동과 확장 필드 저장은 확인했지만 변경 전 개인 데이터 전체 비교 및 DDL별 로그 수집은 하지 않았다.
- 생성 시각의 실제 DB 값 비교와 원본 API/DB 구조는 미확인이다. 언어·악센트·collation 검색 결과가 원본과 같은지도 미확인이다.
- 기존 개인 메모는 변경·삭제하지 않았다. 최종 데모는 과제용 메모 ID 3/4와 라벨 ID 1이며, 삭제 검증용 ID 5 및 임시 라벨 ID 2만 영구 삭제했다.

## 10. 제출 파일과 비공개 제외

앱 소스·테스트·SQL·Wrapper·실행 스크립트·한국어 문서·검수한 정제 증거만 제출한다. `.rea-setup-backup/`, `app/target/`, 비밀번호·키·토큰·개인 메모 파일·브라우저 프로필·쿠키·원시 DOM/HAR·터미널 대화 기록은 제외한다. DB 데이터/덤프는 제출하지 않는다. 알려진 비밀값 패턴 검사와 파일 목록·diff·이미지 검수를 수행했으며, 패턴 검사가 모든 종류의 비밀값 부재를 수학적으로 보장하는 것은 아니다.

제출 준비 점검: 후보 67개 파일, 4개 증거 폴더의 해시 19개 모두 일치, DOM 확인 69개 모두 일치, git diff 공백 오류 없음. 현재 에이전트 환경에서 `.git/index.lock` 생성이 `Operation not permitted`로 차단되어 새 커밋·푸시는 미완료다. 확인한 기존 HEAD는 `1ef15e141e2b04b1b319ef61f6d54da6822055e7`, 브랜치는 main, 원격은 `https://github.com/bae-seung/rea-keep.git`이다. 이 기존 해시를 제출 확정 커밋으로 표시하지 않는다.
